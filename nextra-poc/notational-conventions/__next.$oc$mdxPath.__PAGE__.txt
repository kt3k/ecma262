      <p>Input elements other than white space and comments form the terminal symbols for the syntactic grammar for ECMAScript and are called ECMAScript <em>tokens</em>. These tokens are the <emu-xref href="/ecma262/nextra-poc/ecmascript-language-lexical-grammar#sec-keywords-and-reserved-words"><a href="/ecma262/nextra-poc/ecmascript-language-lexical-grammar#sec-keywords-and-reserved-words">reserved words</a></emu-xref>, identifiers, literals, and punctuators of the ECMAScript language. Simple white space and single-line comments are discarded and do not appear in the stream of input elements for the syntactic grammar. A <emu-nt><a href="/ecma262/nextra-poc/additional-ecmascript-features-for-web-browsers#prod-MultiLineComment">MultiLineComment</a></emu-nt> (that is, a comment of the form <code>/*</code>…<code>*/</code> regardless of whether it spans more than one line) is likewise simply discarded if it contains no line terminator; but if a <emu-nt><a href="/ecma262/nextra-poc/additional-ecmascript-features-for-web-browsers#prod-MultiLineComment">MultiLineComment</a></emu-nt> contains one or more line terminators, then it is replaced by a single line terminator, which becomes part of the stream of input elements for the syntactic grammar.</p>
      <p>A <em>RegExp grammar</em> for ECMAScript is given in <emu-xref href="#sec-patterns"><a href="/ecma262/nextra-poc/text-processing#sec-patterns">22.2.1</a></emu-xref>. It defines a set of productions, starting from the <emu-xref href="/ecma262/nextra-poc/notational-conventions#sec-context-free-grammars"><a href="/ecma262/nextra-poc/notational-conventions#sec-context-free-grammars">goal symbol</a></emu-xref> <emu-nt><a href="/ecma262/nextra-poc/text-processing#prod-Pattern">Pattern</a></emu-nt>, that describe how sequences of code points are translated into regular expression patterns.</p>
      <p>Productions of the lexical and RegExp grammars are distinguished by having two colons “<b>::</b>” as separating punctuation. The lexical and RegExp grammars share some productions.</p>

14:T1fae,<p>The <em>syntactic grammar</em> for ECMAScript is given in clauses <emu-xref href="#sec-ecmascript-language-expressions"><a href="/ecma262/nextra-poc/ecmascript-language-expressions#sec-ecmascript-language-expressions">13</a></emu-xref> through <emu-xref href="#sec-ecmascript-language-scripts-and-modules"><a href="/ecma262/nextra-poc/ecmascript-language-scripts-and-modules#sec-ecmascript-language-scripts-and-modules">16</a></emu-xref>. This grammar has ECMAScript tokens defined by the lexical grammar as its terminal symbols (<emu-xref href="#sec-lexical-and-regexp-grammars"><a href="/ecma262/nextra-poc/notational-conventions#sec-lexical-and-regexp-grammars">5.1.2</a></emu-xref>). It defines a set of productions, starting from two alternative <emu-xref href="/ecma262/nextra-poc/notational-conventions#sec-context-free-grammars"><a href="/ecma262/nextra-poc/notational-conventions#sec-context-free-grammars">goal symbols</a></emu-xref> <emu-nt><a href="/ecma262/nextra-poc/ecmascript-language-scripts-and-modules#prod-Script">Script</a></emu-nt> and <emu-nt><a href="/ecma262/nextra-poc/ecmascript-language-scripts-and-modules#prod-Module">Module</a></emu-nt>, that describe how sequences of tokens form syntactically correct independent components of ECMAScript programs.</p>
      <p>When a stream of code points is to be parsed as an ECMAScript <emu-nt><a href="/ecma262/nextra-poc/ecmascript-language-scripts-and-modules#prod-Script">Script</a></emu-nt> or <emu-nt><a href="/ecma262/nextra-poc/ecmascript-language-scripts-and-modules#prod-Module">Module</a></emu-nt>, it is first converted to a stream of input elements by repeated application of the lexical grammar; this stream of input elements is then parsed by a single application of the syntactic grammar. The input stream is syntactically in error if the tokens in the stream of input elements cannot be parsed as a single instance of the goal nonterminal (<emu-nt><a href="/ecma262/nextra-poc/ecmascript-language-scripts-and-modules#prod-Script">Script</a></emu-nt> or <emu-nt><a href="/ecma262/nextra-poc/ecmascript-language-scripts-and-modules#prod-Module">Module</a></emu-nt>), with no tokens left over.</p>
      <p>When a parse is successful, it constructs a <em>parse tree</em>, a rooted tree structure in which each node is a <dfn variants="Parse Nodes">Parse Node</dfn>. Each Parse Node is an <em>instance</em> of a symbol in the grammar; it represents a span of the source text that can be derived from that symbol. The root node of the parse tree, representing the whole of the source text, is an instance of the parse's <emu-xref href="/ecma262/nextra-poc/notational-conventions#sec-context-free-grammars"><a href="/ecma262/nextra-poc/notational-conventions#sec-context-free-grammars">goal symbol</a></emu-xref>. When a Parse Node is an instance of a nonterminal, it is also an instance of some production that has that nonterminal as its left-hand side. Moreover, it has zero or more <em>children</em>, one for each symbol on the production's right-hand side: each child is a Parse Node that is an instance of the corresponding symbol.</p>
      <p>New Parse Nodes are instantiated for each invocation of the parser and never reused between parses even of identical source text. Parse Nodes are considered <dfn>the same Parse Node</dfn> if and only if they represent the same span of source text, are instances of the same grammar symbol, and resulted from the same parser invocation.</p>
      <emu-note data-num="1"><span class="note">Note 1</span><div class="note-contents">
        <p>Parsing the same String multiple times will lead to different Parse Nodes. For example, consider:</p>
        <pre><code class="hljs javascript">
          <span class="hljs-keyword">let</span> str = <span class="hljs-string">&quot;1 + 1;&quot;</span>;
          <span class="hljs-built_in">eval</span>(str);
          <span class="hljs-built_in">eval</span>(str);
        </code></pre>
        <p>Each call to <code>eval</code> converts the value of <code>str</code> into <emu-xref href="/ecma262/nextra-poc/ecmascript-language-source-code#sec-source-text"><a href="/ecma262/nextra-poc/ecmascript-language-source-code#sec-source-text">ECMAScript source text</a></emu-xref> and performs an independent parse that creates its own separate tree of Parse Nodes. The trees are distinct even though each parse operates upon a source text that was derived from the same String value.</p>
      </div></emu-note>
      <emu-note data-num="2"><span class="note">Note 2</span><div class="note-contents">Parse Nodes are specification artefacts, and implementations are not required to use an analogous data structure.</div></emu-note>
      <p>Productions of the syntactic grammar are distinguished by having just one colon “<b>:</b>” as punctuation.</p>
      <p>The syntactic grammar as presented in clauses <emu-xref href="#sec-ecmascript-language-expressions"><a href="/ecma262/nextra-poc/ecmascript-language-expressions#sec-ecmascript-language-expressions">13</a></emu-xref> through <emu-xref href="#sec-ecmascript-language-scripts-and-modules"><a href="/ecma262/nextra-poc/ecmascript-language-scripts-and-modules#sec-ecmascript-language-scripts-and-modules">16</a></emu-xref> is not a complete account of which token sequences are accepted as a correct ECMAScript <emu-nt><a href="/ecma262/nextra-poc/ecmascript-language-scripts-and-modules#prod-Script">Script</a></emu-nt> or <emu-nt><a href="/ecma262/nextra-poc/ecmascript-language-scripts-and-modules#prod-Module">Module</a></emu-nt>. Certain additional token sequences are also accepted, namely, those that would be described by the grammar if only semicolons were added to the sequence in certain places (such as before line terminator characters). Furthermore, certain token sequences that are described by the grammar are not considered acceptable if a line terminator character appears in certain “awkward” places.</p>
      <p>In certain cases, in order to avoid ambiguities, the syntactic grammar uses generalized productions that permit token sequences that do not form a valid ECMAScript <emu-nt><a href="/ecma262/nextra-poc/ecmascript-language-scripts-and-modules#prod-Script">Script</a></emu-nt> or <emu-nt><a href="/ecma262/nextra-poc/ecmascript-language-scripts-and-modules#prod-Module">Module</a></emu-nt>. For example, this technique is used for object literals and object destructuring patterns. In such cases a more restrictive <em>supplemental grammar</em> is provided that further restricts the acceptable token sequences. Typically, an <emu-xref href="/ecma262/nextra-poc/error-handling-and-language-extensions#early-error"><a href="/ecma262/nextra-poc/error-handling-and-language-extensions#early-error">early error</a></emu-xref> rule will then state that, in certain contexts, “<var>p</var> <dfn id="must-cover">must cover</dfn> an <var>n</var>”, where <var>p</var> is a Parse Node (an instance of the generalized production) and <var>n</var> is a nonterminal from the supplemental grammar. This means:</p>
      <ol>
        <li>The sequence of tokens originally matched by <var>p</var> is parsed again using <var>n</var> as the <emu-xref href="/ecma262/nextra-poc/notational-conventions#sec-context-free-grammars"><a href="/ecma262/nextra-poc/notational-conventions#sec-context-free-grammars">goal symbol</a></emu-xref>. 1f:Tf3b,<p>The specification often uses a numbered list to specify steps in an algorithm. These algorithms are used to precisely specify the required semantics of ECMAScript language constructs. The algorithms are not intended to imply the use of any specific implementation technique. In practice, there may be more efficient algorithms available to implement a given feature.</p>
    <p>Algorithms may be explicitly parameterized with an ordered, comma-separated sequence of alias names which may be used within the algorithm steps to reference the argument passed in that position. Optional parameters are denoted with surrounding brackets ([ , <var>name</var> ]) and are no different from required parameters within algorithm steps. A rest parameter may appear at the end of a parameter list, denoted with leading ellipsis (, ...<var>name</var>). The rest parameter captures all of the arguments provided following the required and optional parameters into a <emu-xref href="/ecma262/nextra-poc/ecmascript-data-types-and-values#sec-list-and-record-specification-type"><a href="/ecma262/nextra-poc/ecmascript-data-types-and-values#sec-list-and-record-specification-type">List</a></emu-xref>.     <p>Algorithm steps may be subdivided into sequential substeps. Substeps are indented and may themselves be further divided into indented substeps. Outline numbering conventions are used to identify substeps with the first level of substeps labelled with lowercase alphabetic characters and the second level of substeps labelled with lowercase roman numerals. If more than three levels are required these rules repeat with the fourth level using numeric labels. For example:</p>
    <emu-alg example><ol><li>Top-level step<ol><li>Substep.</li><li>Substep.<ol><li>Subsubstep.<ol><li>Subsubsubstep<ol><li>Subsubsubsubstep<ol><li>Subsubsubsubsubstep</li></ol></li></ol></li></ol></li></ol></li></ol></li></ol></emu-alg>

    <p>A step may begin with “For each” or “Repeat” to specify the iterative application of its substeps.</p>
    <p>A step that begins with “<dfn id="assert">Assert</dfn>:” asserts an invariant condition of its algorithm. Such assertions are used to make explicit algorithmic invariants that would otherwise be implicit. Assertion steps and note steps are strictly informative; they add no additional semantic requirements and hence need not be checked by an implementation.</p>
    <p>Algorithm steps may declare named aliases for any value using the form “Let <var>x</var> be <var>someValue</var>”. When applied to <emu-xref href="/ecma262/nextra-poc/notational-conventions#extended-mathematical-value"><a href="/ecma262/nextra-poc/notational-conventions#extended-mathematical-value">extended mathematical values</a></emu-xref>, the operators refer to the usual mathematical operations over the extended real numbers; indeterminate forms are not defined and their use in this specification should be considered an editorial error. When applied to BigInts, the operators refer to the usual mathematical operations applied to the <emu-xref href="/ecma262/nextra-poc/notational-conventions#mathematical-value-of"><a href="/ecma262/nextra-poc/notational-conventions#mathematical-value-of">mathematical value of</a></emu-xref> the BigInt. Numeric operators applied to mixed-type operands (such as a Number and a <emu-xref href="/ecma262/nextra-poc/notational-conventions#mathematical-value"><a href="/ecma262/nextra-poc/notational-conventions#mathematical-value">mathematical value</a></emu-xref>) are not defined and should be considered an editorial error in this specification.</p>
      <p>Conversions between <emu-xref href="/ecma262/nextra-poc/notational-conventions#mathematical-value"><a href="/ecma262/nextra-poc/notational-conventions#mathematical-value">mathematical values</a></emu-xref> and Numbers or BigInts are always explicit in this document. A conversion from a <emu-xref href="/ecma262/nextra-poc/notational-conventions#mathematical-value"><a href="/ecma262/nextra-poc/notational-conventions#mathematical-value">mathematical value</a></emu-xref> or <emu-xref href="/ecma262/nextra-poc/notational-conventions#extended-mathematical-value"><a href="/ecma262/nextra-poc/notational-conventions#extended-mathematical-value">extended mathematical value</a></emu-xref> <var>x</var> to a Number is denoted as “the <emu-xref href="/ecma262/nextra-poc/ecmascript-data-types-and-values#number-value-for"><a href="/ecma262/nextra-poc/ecmascript-data-types-and-values#number-value-for">Number value for</a></emu-xref> <var>x</var>” or <emu-eqn class="inline" id="𝔽" aoid="𝔽">𝔽(<var>x</var>)</emu-eqn>, and is defined in <emu-xref href="#sec-ecmascript-language-types-number-type"><a href="/ecma262/nextra-poc/ecmascript-data-types-and-values#sec-ecmascript-language-types-number-type">6.1.6.1</a></emu-xref>. A conversion from an <emu-xref href="/ecma262/nextra-poc/notational-conventions#integer"><a href="/ecma262/nextra-poc/notational-conventions#integer">integer</a></emu-xref> <var>x</var> to a BigInt is denoted as “the <dfn id="bigint-value-for">BigInt value for</dfn> <var>x</var>” or <emu-eqn class="inline" id="ℤ" aoid="ℤ">ℤ(<var>x</var>)</emu-eqn>. A conversion from a Number or BigInt <var>x</var> to a <emu-xref href="/ecma262/nextra-poc/notational-conventions#mathematical-value"><a href="/ecma262/nextra-poc/notational-conventions#mathematical-value">mathematical value</a></emu-xref> is denoted as “the <dfn id="mathematical-value-of">mathematical value of</dfn> <var>x</var>”, or <emu-eqn class="inline" id="ℝ" aoid="ℝ">ℝ(<var>x</var>)</emu-eqn>. The <emu-xref href="/ecma262/nextra-poc/notational-conventions#mathematical-value-of"><a href="/ecma262/nextra-poc/notational-conventions#mathematical-value-of">mathematical value of</a></emu-xref> <emu-val>+0</emu-val><sub>𝔽</sub> and <emu-val>-0</emu-val><sub>𝔽</sub> is the <emu-xref href="/ecma262/nextra-poc/notational-conventions#mathematical-value"><a href="/ecma262/nextra-poc/notational-conventions#mathematical-value">mathematical value</a></emu-xref> 0. The <emu-xref href="/ecma262/nextra-poc/notational-conventions#mathematical-value-of"><a href="/ecma262/nextra-poc/notational-conventions#mathematical-value-of">mathematical value of</a></emu-xref> non-<emu-xref href="/ecma262/nextra-poc/ecmascript-data-types-and-values#finite"><a href="/ecma262/nextra-poc/ecmascript-data-types-and-values#finite">finite</a></emu-xref> values is not defined. The <dfn id="extended-mathematical-value-of">extended mathematical value of</dfn> <var>x</var> is the <emu-xref href="/ecma262/nextra-poc/notational-conventions#mathematical-value-of"><a href="/ecma262/nextra-poc/notational-conventions#mathematical-value-of">mathematical value of</a></emu-xref> <var>x</var> for <emu-xref href="/ecma262/nextra-poc/ecmascript-data-types-and-values#finite"><a href="/ecma262/nextra-poc/ecmascript-data-types-and-values#finite">finite</a></emu-xref> values, and is +∞ and -∞ for <emu-val>+∞</emu-val><sub>𝔽</sub> and <emu-val>-∞</emu-val><sub>𝔽</sub> respectively; it is not defined for <emu-val>NaN</emu-val>.</p>
      <p>The mathematical function <emu-eqn class="inline" id="eqn-abs" aoid="abs">abs(<var>x</var>)</emu-eqn> produces the absolute value of <var>x</var>, which is <emu-eqn class="inline">-<var>x</var></emu-eqn> if <var>x</var> &lt; 0 and otherwise is <var>x</var> itself.</p>
      <p>The mathematical function <emu-eqn class="inline" id="eqn-ln" aoid="ln">ln(<var>x</var>)</emu-eqn> produces the natural logarithm of <var>x</var>. The mathematical function <emu-eqn class="inline" id="eqn-log10" aoid="log10">log10(<var>x</var>)</emu-eqn> produces the base 10 logarithm of <var>x</var>. The mathematical function <emu-eqn class="inline" id="eqn-log2" aoid="log2">log2(<var>x</var>)</emu-eqn> produces the base 2 logarithm of <var>x</var>.</p>
      <p>The mathematical function <emu-eqn class="inline" id="eqn-min" aoid="min">min(<var>x1</var>, <var>x2</var>, … , <var>xN</var>)</emu-eqn> produces the mathematically smallest of <emu-eqn class="inline"><var>x1</var></emu-eqn> through <emu-eqn class="inline"><var>xN</var></emu-eqn>. The mathematical function <emu-eqn class="inline" id="eqn-max" aoid="max">max(<var>x1</var>, <var>x2</var>, ..., <var>xN</var>)</emu-eqn> produces the mathematically largest of <emu-eqn class="inline"><var>x1</var></emu-eqn> through <emu-eqn class="inline"><var>xN</var></emu-eqn>. The domain and range of these mathematical functions are the <emu-xref href="/ecma262/nextra-poc/notational-conventions#extended-mathematical-value"><a href="/ecma262/nextra-poc/notational-conventions#extended-mathematical-value">extended mathematical values</a></emu-xref>.</p>
      <p>The notation “<emu-eqn class="inline" id="eqn-modulo" aoid="modulo"><var>x</var> modulo <var>y</var></emu-eqn>” (<var>y</var> must be <emu-xref href="/ecma262/nextra-poc/ecmascript-data-types-and-values#finite"><a href="/ecma262/nextra-poc/ecmascript-data-types-and-values#finite">finite</a></emu-xref> and non-zero) computes a value <var>k</var> of the same sign as <var>y</var> (or zero) such that <emu-eqn class="inline"><emu-xref aoid="abs"><a href="/ecma262/nextra-poc/notational-conventions#eqn-abs">abs</a></emu-xref>(<var>k</var>) &lt; <emu-xref aoid="abs"><a href="/ecma262/nextra-poc/notational-conventions#eqn-abs">abs</a></emu-xref>(<var>y</var>) and <var>x</var> - <var>k</var> = <var>q</var> × <var>y</var></emu-eqn> for some <emu-xref href="/ecma262/nextra-poc/notational-conventions#integer"><a href="/ecma262/nextra-poc/notational-conventions#integer">integer</a></emu-xref> <var>q</var>.</p>
      <p>The phrase “the result of <dfn id="clamping">clamping</dfn> <var>x</var> between <var>lower</var> and <var>upper</var>” (where <var>x</var> is an <emu-xref href="/ecma262/nextra-poc/notational-conventions#extended-mathematical-value"><a href="/ecma262/nextra-poc/notational-conventions#extended-mathematical-value">extended mathematical value</a></emu-xref> and <var>lower</var> and <var>upper</var> are <emu-xref href="/ecma262/nextra-poc/notational-conventions#mathematical-value"><a href="/ecma262/nextra-poc/notational-conventions#mathematical-value">mathematical values</a></emu-xref> such that <var>lower</var> ≤ <var>upper</var>) produces <var>lower</var> if <var>x</var> &lt; <var>lower</var>, produces <var>upper</var> if <var>x</var> > <var>upper</var>, and otherwise produces <var>x</var>.</p>
      <p>The mathematical function <emu-eqn class="inline" id="eqn-floor" aoid="floor">floor(<var>x</var>)</emu-eqn> produces the largest <emu-xref href="/ecma262/nextra-poc/notational-conventions#integer"><a href="/ecma262/nextra-poc/notational-conventions#integer">integer</a></emu-xref> (closest to +∞) that is not larger than <var>x</var>.</p>
      <emu-note><span class="note">Note</span><div class="note-contents">
        <p><emu-eqn class="inline"><emu-xref aoid="floor"><a href="/ecma262/nextra-poc/notational-conventions#eqn-floor">floor</a></emu-xref>(<var>x</var>) = <var>x</var> - (<var>x</var> <emu-xref aoid="modulo"><a href="/ecma262/nextra-poc/notational-conventions#eqn-modulo">modulo</a></emu-xref> 1)</emu-eqn>.</p>
      </div></emu-note>
      <p>The mathematical function <emu-eqn class="inline" id="eqn-truncate" aoid="truncate">truncate(<var>x</var>)</emu-eqn> removes the fractional part of <var>x</var> by rounding towards zero, producing <emu-eqn class="inline">-<emu-xref aoid="floor"><a href="/ecma262/nextra-poc/notational-conventions#eqn-floor">floor</a></emu-xref>(-<var>x</var>)</emu-eqn> if <var>x</var> &lt; 0 and otherwise producing <emu-eqn class="inline"><emu-xref aoid="floor"><a href="/ecma262/nextra-poc/notational-conventions#eqn-floor">floor</a></emu-xref>(<var>x</var>)</emu-eqn>.</p>
      <p>Mathematical functions <emu-xref aoid="min"><a href="/ecma262/nextra-poc/notational-conventions#eqn-min">min</a></emu-xref>, <emu-xref aoid="max"><a href="/ecma262/nextra-poc/notational-conventions#eqn-max">max</a></emu-xref>, <emu-xref aoid="abs"><a href="/ecma262/nextra-poc/notational-conventions#eqn-abs">abs</a></emu-xref>, <emu-xref aoid="floor"><a href="/ecma262/nextra-poc/notational-conventions#eqn-floor">floor</a></emu-xref>, and <emu-xref aoid="truncate"><a href="/ecma262/nextra-poc/notational-conventions#eqn-truncate">truncate</a></emu-xref> are not defined for Numbers and BigInts, and any usage of those methods that have non-<emu-xref href="/ecma262/nextra-poc/notational-conventions#mathematical-value"><a href="/ecma262/nextra-poc/notational-conventions#mathematical-value">mathematical value</a></emu-xref> arguments would be an editorial error in this specification.</p>
      <p>An <dfn id="interval">interval</dfn> from lower bound <var>a</var> to upper bound <var>b</var> is a possibly-infinite, possibly-empty set of numeric values of the same numeric type. Each bound will be described as either inclusive or exclusive, but not both. There are four kinds of intervals, as follows:</p>
      <ul>
        <li>An <emu-xref href="/ecma262/nextra-poc/notational-conventions#interval"><a href="/ecma262/nextra-poc/notational-conventions#interval">interval</a></emu-xref> from <var>a</var> (inclusive) to <var>b</var> (inclusive), also called an <dfn id="inclusive-interval">inclusive interval</dfn> from <var>a</var> to <var>b</var>, includes all values <var>x</var> of the same numeric type such that <var>a</var> ≤ <var>x</var> ≤ <var>b</var>, and no others.</li>
        <li>An <emu-xref href="/ecma262/nextra-poc/notational-conventions#interval"><a href="/ecma262/nextra-poc/notational-conventions#interval">interval</a></emu-xref> from <var>a</var> (inclusive) to <var>b</var> (exclusive) includes all values <var>x</var> of the same numeric type such that <var>a</var> ≤ <var>x</var> &lt; <var>b</var>, and no others.</li>
        <li>An <emu-xref href="/ecma262/nextra-poc/notational-conventions#interval"><a href="/ecma262/nextra-poc/notational-conventions#interval">interval</a></emu-xref> from <var>a</var> (exclusive) to <var>b</var> (inclusive) includes all values <var>x</var> of the same numeric type such that <var>a</var> &lt; <var>x</var> ≤ <var>b</var>, and no others.</li>
        <li>An <emu-xref href="/ecma262/nextra-poc/notational-conventions#interval"><a href="/ecma262/nextra-poc/notational-conventions#interval">interval</a></emu-xref> from <var>a</var> (exclusive) to <var>b</var> (exclusive) includes all values <var>x</var> of the same numeric type such that <var>a</var> &lt; <var>x</var> &lt; <var>b</var>, and no others.</li>
      </ul>
      <p>For example, the <emu-xref href="/ecma262/nextra-poc/notational-conventions#interval"><a href="/ecma262/nextra-poc/notational-conventions#interval">interval</a></emu-xref> from 1 (inclusive) to 2 (exclusive) consists of all <emu-xref href="/ecma262/nextra-poc/notational-conventions#mathematical-value"><a href="/ecma262/nextra-poc/notational-conventions#mathematical-value">mathematical values</a></emu-xref> between 1 and 2, including 1 and not including 2. For the purpose of defining intervals, <emu-val>-0</emu-val><sub>𝔽</sub> &lt; <!-- this comment here to avoid ecmarkup complaining about comparison to 0 --> <emu-val>+0</emu-val><sub>𝔽</sub>, so, for example, an <emu-xref href="/ecma262/nextra-poc/notational-conventions#inclusive-interval"><a href="/ecma262/nextra-poc/notational-conventions#inclusive-interval">inclusive interval</a></emu-xref> with a lower bound of <emu-val>+0</emu-val><sub>𝔽</sub> includes <emu-val>+0</emu-val><sub>𝔽</sub> but not <emu-val>-0</emu-val><sub>𝔽</sub>. <emu-val>NaN</emu-val> is never included in an <emu-xref href="/ecma262/nextra-poc/notational-conventions#interval"><a href="/ecma262/nextra-poc/notational-conventions#interval">interval</a></emu-xref>.</p>

36:T2d9a,<p>In this specification, both specification values and <emu-xref href="/ecma262/nextra-poc/ecmascript-data-types-and-values#sec-ecmascript-language-types"><a href="/ecma262/nextra-poc/ecmascript-data-types-and-values#sec-ecmascript-language-types">ECMAScript language values</a></emu-xref> are compared for equality. When comparing for equality, values fall into one of two categories. <dfn variants="values without identity,value without identity">Values without identity</dfn> are equal to other values without identity if all of their innate characteristics are the same — characteristics such as the magnitude of an <emu-xref href="/ecma262/nextra-poc/notational-conventions#integer"><a href="/ecma262/nextra-poc/notational-conventions#integer">integer</a></emu-xref> or the length of a sequence. Values without identity may be manifest without prior reference by fully describing their characteristics. In contrast, each <dfn variants="values with identity">value with identity</dfn> is unique and therefore only equal to itself. Values with identity are like values without identity but with an additional unguessable, unchangeable, universally-unique characteristic called <em>identity</em>. References to existing values with identity cannot be manifest simply by describing them, as the identity itself is indescribable; instead, references to these values must be explicitly passed from one place to another. Some values with identity are mutable and therefore can have their characteristics (except their identity) changed in-place, causing all holders of the value to observe the new characteristics. A value without identity is never equal to a value with identity.</p>
      <p>From the perspective of this specification, the word “is” is used to compare two values for equality, as in “If <var>bool</var> is <emu-val>true</emu-val>, then ...”, and the word “contains” is used to search for a value inside lists using equality comparisons, as in “If <var>list</var> contains a <emu-xref href="/ecma262/nextra-poc/ecmascript-data-types-and-values#sec-list-and-record-specification-type"><a href="/ecma262/nextra-poc/ecmascript-data-types-and-values#sec-list-and-record-specification-type">Record</a></emu-xref> <var>r</var> such that <var>r</var>.<var class="field">[[Foo]]</var> is <emu-val>true</emu-val>, then ...”. The <em>specification identity</em> of values determines the result of these comparisons and is axiomatic in this specification.</p>

The algorithms of these comparison <emu-xref href="/ecma262/nextra-poc/notational-conventions#sec-algorithm-conventions-abstract-operations"><a href="/ecma262/nextra-poc/notational-conventions#sec-algorithm-conventions-abstract-operations">abstract operations</a></emu-xref> determine <em>language identity</em> of <emu-xref href="/ecma262/nextra-poc/ecmascript-data-types-and-values#sec-ecmascript-language-types"><a href="/ecma262/nextra-poc/ecmascript-data-types-and-values#sec-ecmascript-language-types">ECMAScript language values</a></emu-xref>.</p>
